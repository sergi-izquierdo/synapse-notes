\section{Arquitectura general (C4)}
\label{sec:arquitectura-c4-disseny}

L'arquitectura del sistema està descrita en dos nivells del model C4 \parencite{brown2018c4}: \emph{Context} (qui interactua amb el sistema) i \emph{Containers} (quins runtimes el componen). Una vista més detallada de cada container, amb mòduls interns i la seva implementació concreta, està al capítol d'implementació (\S\ref{sec:c4-containers}); aquesta secció recull només els arguments arquitectònics que sustenten cada decisió.

\subsection{Vista de Context (C4 nivell 1)}

Els actors externs identificats són tres:

\begin{itemize}
    \item \textbf{L'usuari humà} (autor de les notes), que interactua via navegador web amb l'aplicació Next.js i amb el xat RAG.
    \item \textbf{Un agent extern compatible amb MCP} (típicament Claude Desktop, també PRs d'agents personalitzats), que es connecta al servidor MCP amb les credencials de l'usuari per realitzar operacions des de fora del navegador.
    \item \textbf{Els proveïdors externs d'IA}: Anthropic per al model de xat, judge i sumarització; Google per als embeddings vectorials.
\end{itemize}

El sistema és deliberadament \emph{single-tenant a la pràctica} (vegeu \S\ref{sec:trifecta} i el capítol \ref{ch:requisits}): l'arquitectura admet múltiples usuaris via RLS, però l'allowlist actual a producció (decisió D4) limita la població autoritzada a un únic UID. Aquesta limitació és operacional, no estructural: tota la lògica de seguretat ja gestiona contextos d'autenticació separats per usuari.

\subsection{Vista de Containers (C4 nivell 2)}

L'arquitectura es desplega en quatre runtimes lògics:

\begin{enumerate}
    \item \textbf{Aplicació web Next.js} (Vercel, runtime Node.js): App Router amb Server Components per al render inicial, Server Actions per a mutacions, i tres rutes HTTP que escalen sota Fluid Compute: \texttt{/api/chat} (xat RAG amb streaming), \texttt{/api/mcp} (servidor MCP via JSON-RPC sobre StreamableHTTP), \texttt{/api/suggest-tags} (tagging via LLM estructurat).
    \item \textbf{Base de dades Supabase}: PostgreSQL 15+ amb pgvector activat i Supabase Auth per a OAuth (Google + GitHub). RLS és el mecanisme exclusiu d'autorització de fila. Els agents en segon pla viuen al runtime Vercel via rutes cron (\S\ref{sec:disseny-agents}), no a Edge Functions de Supabase.
    \item \textbf{Proveïdors d'IA}: Anthropic Haiku 4.5 i Google Gemini, accedits via el Vercel AI SDK des del costat servidor. Mai des del client per evitar exposar API keys.
    \item \textbf{Client MCP extern} (opcional): Claude Desktop o un agent custom que es connecta al servidor MCP amb un JWT vàlid del compte d'usuari.
\end{enumerate}

Les decisions arquitectòniques majors que justifiquen aquesta partició estan al registre de decisions (\texttt{docs/tfg/00-decision-log.md}, D1 a D5). Resumim les que afecten directament la vista de containers:

\paragraph{Why Next.js + Vercel.} Una única codebase per al client i el servidor (Server Components + Server Actions), tota la superfície AI gestionada al servidor (mai exposem API keys al navegador), i Fluid Compute per a respondre amb baixa latència sense gestionar contenidors. El cost operatiu inicial és zero (free tier de Vercel + Supabase) i escalable sense reescriure res.

\paragraph{Why Supabase (no Prisma + Postgres self-hosted).} Auth + Postgres + Edge Functions com a un sol proveïdor evita haver de mantenir tres serveis separats. Més important: la integració d'RLS amb el JWT que el navegador envia a cada request permet eliminar tota la lògica d'autorització de l'aplicació, perquè la base de dades mateixa rebutja queries no autoritzades. És una decisió que canvia el plantejament del backend: en lloc d'\emph{aplicar} controls d'accés al codi, els \emph{declarem} a la base de dades.

\paragraph{Why pgvector (no Pinecone, Qdrant, o un vector store extern).} Amb el corpus actual (50 notes / usuari) i fins als límits que es preveuen al §11 Costos, pgvector és més que suficient i té tres avantatges decisius: viu dins la mateixa instància que les dades transaccionals (els joins de RLS funcionen), no afegeix una dependència externa, i el seu HNSW index és prou ràpid per al volum del producte. Si el corpus creix tres ordres de magnitud, és el primer punt a re-avaluar.

\paragraph{Why MCP (no REST API tradicional + clau d'API).} Un servidor MCP exposa les eines a agents externs de manera tipada (JSON Schema), amb \emph{host confirmation} per defecte per a mutations (decisió D2). És el patró específicament dissenyat per al cas d'ús: una eina que un agent extern (Claude Desktop) pot cridar amb les credencials del seu usuari humà sense que el servidor hagi de gestionar API keys per a cada agent. La JWT que envia el client MCP és la mateixa que el navegador hauria enviat, i RLS la valida idèntica.

\subsection{Polítiques RLS per taula}

Cada taula del model té RLS activa des de la seva migració de creació. La política base és sempre \texttt{user\_id = auth.uid()}, és a dir, l'usuari només pot llegir/modificar les seves pròpies files. Les particularitats per taula són:

\begin{itemize}
    \item \texttt{notes}: les quatre operacions (SELECT, INSERT, UPDATE, DELETE) tenen política independent. Després d'un incident reproduït amb \texttt{chats} a l'abril (el \texttt{supabase-js} retorna \texttt{error: null} amb \texttt{rowCount: 0} davant una política DELETE no definida en lloc de fallar visiblement), totes les taules noves del projecte porten les quatre polítiques per defecte. Aquest \emph{forat silenciós} està documentat al capítol~\ref{ch:valoracio} com a lliçó apresa.
    \item \texttt{messages}: la política llegeix \texttt{chat\_id} i ho creua amb \texttt{chats.user\_id} per delegar la propietat al pare. És l'única taula del model que no porta \texttt{user\_id} directe; el cost d'un join al SELECT és acceptable perquè els missatges ja s'accedeixen sempre per \texttt{chat\_id}.
    \item \texttt{agent\_events}: només té política SELECT (\texttt{FOR SELECT USING user\_id = auth.uid()}). L'append és deliberadament restringit a service-role per evitar que un client pugui falsificar audit logs.
    \item \texttt{note\_links}: les polítiques (SELECT, INSERT, UPDATE, DELETE) llegeixen \texttt{user\_id} denormalitzat per evitar el join cap a \texttt{notes}, perquè les operacions de graph fan moltíssimes lectures de \texttt{note\_links} i un join per cada una seria un coll d'ampolla.
\end{itemize}

\subsection{Índexs}

\paragraph{Índex vectorial.} El més important és \texttt{notes\_user\_embedding\_idx}, un HNSW (Hierarchical Navigable Small World) sobre \texttt{notes.embedding} amb operador \texttt{vector\_cosine\_ops}. És \emph{parcial} (\texttt{WHERE embedding IS NOT NULL}) per evitar entrar a l'índex notes acabades de crear que encara no tenen embedding generat. La justificació d'HNSW sobre IVFFlat: HNSW és més car de construir però retorna resultats sense necessitat de tuning d'\texttt{nprobe}, cosa que simplifica el desplegament en un context single-tenant on no calen perfils diferenciats.

\paragraph{Índexs B-tree compostos.} Cada taula porta com a mínim un índex compost (\texttt{user\_id}, \texttt{created\_at DESC}) per a queries del tipus \emph{darreres N notes/xats/events d'aquest usuari}, que són les queries més freqüents al producte. \texttt{tag\_suggestions} té un segon índex per \texttt{(user\_id, status)} per a la query del dashboard que filtra propostes pendents.

\paragraph{Índex de cerca textual.} \texttt{notes.title} té un índex GIN \texttt{lower(title)} amb \texttt{trgm\_ops} per a la cerca \texttt{ILIKE} de l'autocomplete de backlinks (\texttt{[[}, \texttt{@}, \texttt{\#}). El GIN combinat amb pg\_trgm dóna fuzzy matching ràpid sense necessitat d'un FTS Postgres complet, que seria excessiu per al volum del producte.

\subsection{Funcions stored}

Tres funcions amb \texttt{SECURITY INVOKER} (executen amb els permisos del cridador, no del propietari) i \texttt{search\_path} explícit:

\begin{itemize}
    \item \texttt{match\_notes(query\_embedding, match\_threshold, match\_count)}: cerca per similitud cosinus sobre l'HNSW, escau-da a l'usuari via RLS. És la base del RAG i de la cerca semàntica.
    \item \texttt{sync\_note\_links(p\_source\_id, p\_target\_ids[])}: substitueix completament el set d'outgoing edges d'una nota. Patró \emph{replace} en lloc d'incremental per simplificar la consistència; cada save de nota recalcula els \texttt{[[N]]} del seu text i fa una sola crida.
    \item \texttt{get\_note\_graph()}: retorna el graph complet de l'usuari en un sol round-trip, amb arestes de tres tipus: \texttt{tag}, \texttt{embed}, \texttt{link}. Construeix els primers dos via Jaccard sobre tags i cosinus sobre embeddings, i el tercer és una projecció directa de \texttt{note\_links}.
\end{itemize}

Una observació de seguretat documentada a la valoració personal (capítol~\ref{ch:valoracio}): la primera versió de \texttt{get\_note\_graph} portava \texttt{set search\_path = 'public, pg\_catalog'} \emph{amb cometes al voltant de tota la llista}, cosa que Postgres interpreta com \emph{un sol identificador de schema} (\texttt{"public, pg\_catalog"}, que no existeix) en lloc d'una llista. L'efecte: la funció no resolia l'operador \texttt{<=>} de pgvector en runtime. La sintaxi correcta és sense cometes (\texttt{set search\_path = public, pg\_catalog}) i això està rectificat des de la migració \texttt{20260425200000\_get\_note\_graph\_search\_path.sql}.

\section{Disseny del servidor MCP}
\label{sec:disseny-mcp}

Aquesta secció recull les decisions de disseny del servidor MCP (Model Context Protocol \parencite{anthropic2024mcp}) sense reproduir el detall d'implementació, que viu al capítol~\ref{ch:implementacio}, \S\ref{sec:servidor-mcp}. Aquí justifiquem què s'exposa, què no s'exposa, i per què el model d'autenticació adopta JWT passthrough en lloc d'una API key tradicional.

\subsection{Catàleg d'eines}

El servidor exposa 8 eines, 2 resources, i 1 prompt. La selecció és el resultat d'un exercici deliberat de \emph{contenció}: cada eina addicional augmenta la superfície d'atac (vegeu \S\ref{sec:trifecta-matrix}) i el cost de manteniment. La taula~\ref{tab:catàleg-tools} resumeix la decisió.

    \label{tab:catàleg-tools}
    \begin{tabular}{@{}lll>{\raggedright\arraybackslash}p{6cm}@{}}

Les dues \emph{resources} (\texttt{notes://recent} i \texttt{notes://tag/\{tag\}}) ofereixen vistes paginades de notes per a hosts que volen el llistat sencer, no només per cerca. El \emph{prompt} \texttt{daily-review} és una plantilla parametritzable per data que pulla les notes recents i les retorna amb una estructura de 3 seccions (highlights, action items, open threads); es presenta com a prompt MCP perquè el host MCP el suggereixi a l'usuari al començar la sessió.

\subsection{Eines descartades}

Algunes eines aparentment òbvies no s'exposen, amb justificació explícita:

\begin{itemize}
    \item \textbf{\texttt{delete\_note}}: no exposat. Esborrar una nota és una acció irrecuperable. El host MCP no ha d'invocar-la mai com a part d'un flux automatitzat. La UI web ja en proporciona via Server Action, sempre amb confirmació humana.
    \item \textbf{\texttt{export\_all\_notes}} (que bolcaria tot el corpus): no exposat. Aquesta funció és exactament el patró d'exfiltració que el filtre D3 vol prevenir, executat amb intenció.
    \item \textbf{\texttt{set\_user\_preferences}}: no exposat. L'estat de configuració (idioma, tema, agents activats) és prerrogativa de l'usuari, no d'un agent.
    \item \textbf{\texttt{chat\_with\_self}} (que activaria el xat RAG des de l'MCP): no exposat. El xat ja existeix com a producte primari; replicar-lo a l'MCP només duplicaria el codi sense aportar valor.
\end{itemize}

Aquesta llista de descartes és intencional i defensable: el catàleg de 8 eines és el resultat d'una resta deliberada des d'un superconjunt més gran.

\subsection{Autenticació: JWT passthrough en lloc d'API keys}

\paragraph{Decisió.} El servidor MCP no genera ni gestiona API keys per agent. Cada client (Claude Desktop, agent custom, etc.) presenta el JWT de Supabase Auth del seu propietari humà al header \texttt{Authorization: Bearer <jwt>}. El servidor el valida contra Supabase Auth en cada request i el reusa per a tota la sessió MCP.

\paragraph{Per què.} Una API key tradicional (com Stripe, OpenAI o GitHub) crea un tercer principal (la "service account" de l'agent) que cal gestionar separadament: rotar-la, vincular-la a permisos, auditar-la per separat de l'usuari humà. Aquest model afegeix complexitat sense aportar res al cas d'ús personal d'aquest projecte. El JWT de Supabase ja existeix, ja està signat per l'IdP de confiança, ja porta el \texttt{user\_id} que RLS necessita, i té expiració curta (1 h per defecte). Reutilitzar-lo elimina la categoria sencera d'"agent credentials".

\paragraph{Implicació crítica per al disseny.} L'agent (Claude Desktop) actua com a \emph{delegat} de l'usuari humà amb les mateixes credencials. Si l'agent és compromès, l'atacant té les credencials de l'usuari per a totes les eines exposades (vuit) durant el TTL del JWT. La mitigació per a aquest risc residual és D2 \emph{host confirmation}: cada invocació d'una eina mutating al host MCP genera un prompt visible per a l'usuari humà abans de l'execució. La cadena de responsabilitat queda intacta: \textbf{l'agent proposa, l'usuari confirma, el servidor executa}.

\subsection{Transport: StreamableHTTP en lloc de stdio}

\paragraph{Decisió.} El servidor exposa el protocol MCP via HTTP amb el transport \texttt{WebStandardStreamableHTTPServerTransport} del SDK oficial, sobre la ruta \texttt{/api/mcp}. Es descarta el transport \texttt{stdio} (procés local).

\paragraph{Per què.} El servidor és remot per disseny (no es vol que cada usuari instal·li i mantingui un binari Node local). HTTP permet l'allowlist D4 a nivell de ruta, el deploy via Vercel Fluid Compute, i la inspecció via DevTools del navegador per a depurar (\S\ref{sec:red-team-promptfoo} ho explota per a auth manual). La penalització és la complexitat de l'autenticació, que ja queda resolta per la decisió JWT passthrough anterior.

\paragraph{Implicació per al disseny.} El transport StreamableHTTP del SDK requereix que el client envii el header \texttt{Accept: application/json, text/event-stream} per a permetre tant respostes síncrones com streaming. Aquest detall és visible al client (és el primer obstacle que apareix al fer testing manual via DevTools fetch) i s'ha documentat al capítol d'avaluació (\S\ref{sec:red-team-promptfoo}) com a part del protocol del red-team Promptfoo.

\subsection{Mecanisme de confirmation per a mutacions (D2)}

Les eines de categoria \texttt{mutating} (\texttt{create\_note}, \texttt{update\_note}, \texttt{tag\_notes}) i la generativa \texttt{summarise\_notes} estan marcades a la seva \texttt{toolDefinition} amb la convenció \texttt{taskSupport: "forbidden"} reconeguda pels hosts MCP compliants (Claude Desktop l'aplica). Això instrueix el host que ha de demanar confirmació humana per a aquesta crida, fins i tot dins una conversa contínua. \texttt{search\_notes}, \texttt{get\_note} i les eines de graph queden marcades com a \texttt{read-only}-safe i no requereixen confirmació.

Aquest disseny és la línia de defensa explícita davant un atac d'encadenament (l'atacant aconsegueix que \texttt{summarise\_notes} retorni text amb instruccions ocultes; el host les interpretaria i intentaria cridar \texttt{create\_note} per exfiltrar). La confirmation interromp aquesta cadena al pas de mutació.

\section{Disseny dels agents}
\label{sec:disseny-agents}

El sistema contempla tres agents en segon pla que operen sobre el corpus de notes de l'usuari sense intervenció directa. La decisió D5 del registre de decisions (reunió de tutoria 2026-05-21) va reduir l'scope a dos agents implementats i un tercer documentat com a treball futur.

\subsection{Agent \texttt{auto-tag}}

\paragraph{Objectiu.} Proposar etiquetes per a notes que no en tenen (o que en tenen poques) consultant un LLM amb el contingut de la nota i la biblioteca d'etiquetes de l'usuari.

\paragraph{Disseny.} L'agent s'invoca via un cron job diari (Vercel Cron, \texttt{0 3 * * *}). Per a cada usuari de la llista D4, el cron:

\begin{enumerate}
    \item Consulta les notes sense etiquetes (\texttt{tags = \{\}} o \texttt{NULL}), ordenades per \texttt{updated\_at DESC}, limitades a 10 per execució.
    \item Recull la biblioteca d'etiquetes agregant tots els \texttt{tags} únics de les notes vives.
    \item Per a cada nota candidata, crida \texttt{generateObject} amb Haiku 4.5 i un schema Zod que retorna fins a 3 etiquetes existents i opcionalment 1 etiqueta nova en kebab-case.
    \item Escriu les propostes a \texttt{tag\_suggestions} amb estat \texttt{pending}.
    \item Registra un event a \texttt{agent\_events} (agent = \texttt{auto-tag}, action = \texttt{tag.proposed}).
\end{enumerate}

\paragraph{Human-in-the-loop.} L'agent \emph{mai} escriu directament a \texttt{notes.tags}. Les propostes romanen en estat \texttt{pending} fins que l'usuari les accepta o les rebutja des de la UI. Aquesta decisió és deliberada: evita que un LLM amb hallucinations corrompi la taxonomia de l'usuari sense supervisió.

\paragraph{Avaluació.} La secció~\ref{sec:eval-auto-tag} presenta els resultats quantitatius: precision 81{,}3\%, recall 76{,}5\%, F1 78{,}8\% sobre un corpus de 62 notes amb 4 categories.

\subsection{Agent \texttt{weekly-digest}}

\paragraph{Objectiu.} Generar un resum setmanal de l'activitat de l'usuari: notes noves, notes actualitzades, distribució d'etiquetes. El digest es materialitza com una nota més al corpus (etiquetada \texttt{weekly-digest}) per facilitar-ne la consulta posterior.

\paragraph{Disseny.} L'agent s'invoca via un cron job diumenge a les 3 AM UTC (\texttt{0 3 * * 0}). Per a cada usuari:

\begin{enumerate}
    \item Consulta notes amb \texttt{created\_at} dins els últims 7 dies.
    \item Consulta notes amb \texttt{updated\_at} dins els últims 7 dies i \texttt{created\_at} anterior (actualitzacions, no creacions).
    \item Agrega els tags de totes les notes tocades i els ordena per freqüència (top 5).
    \item Formata el digest en Markdown amb seccions: resum numèric, tags actius, llistes de notes noves i actualitzades (amb backlinks \texttt{[[id]]}).
    \item Insereix el digest com a nota nova i registra un event a \texttt{agent\_events}.
\end{enumerate}

\paragraph{Sense LLM.} A diferència de l'auto-tag, el weekly-digest és un agregador pur (SQL + format). No involucra cap crida a LLM, per la qual cosa no necessita filtre D3 ni avaluació de classificació.

\subsection{Agent descartat: \texttt{embedding-backfill}}

L'agent original \texttt{embedding-backfill} hauria recorregut periòdicament les notes amb \texttt{embedding IS NULL} i generat els embeddings via l'API de Gemini. Amb el volum actual (60-70 notes per usuari), els embeddings es generen inline al \texttt{createNote} en temps acceptable ($\sim$1{,}5s) i l'agent no aporta valor operacional. Queda documentat per a corpora 10$\times$ més grans (\S\ref{ch:valoracio}, treball futur).

\subsection{Decisions d'arquitectura de desplegament}

El pla original preveia Supabase Edge Functions amb \texttt{pg\_cron} com a scheduler. La implementació final usa Vercel Cron amb rutes Next.js protegides per un \texttt{CRON\_SECRET} compartit. La decisió és pragmàtica: el prototip TFG opera amb un sol usuari allowlisted (D4) i la infraestructura de cron de Vercel ja existeix. Per a un desplegament multi-tenant, la migració a Edge Functions o a un scheduler extern (Inngest, Trigger.dev) seria el primer canvi a avaluar, perquè el cron de Vercel Hobby limita a execucions diàries.

\section{Disseny de seguretat}
\label{sec:disseny-seguretat}

Aquest capítol presenta el marc de risc del sistema (Lethal Trifecta de Willison), una matriu per eina, i les cinc capes de defensa dissenyades. La verificació empírica d'una d'aquestes capes (D3 LLM-as-judge) està a la secció~\ref{sec:red-team-promptfoo}; la descripció dels mecanismes implementats està al capítol d'implementació (\S\ref{sec:mcp-seguretat}).

\subsection{Marc d'anàlisi: Lethal Trifecta}
\label{sec:trifecta}

Simon Willison va proposar el patró conegut com a \emph{Lethal Trifecta} per a sistemes d'agents amb LLMs i tool calling \parencite{willison2025trifecta}. La hipòtesi és que un atac d'injecció de prompt esdevé una vulnerabilitat de seguretat (no només un comportament inadequat del model) quan tres condicions es donen \textbf{simultàniament} en la mateixa traça d'execució:

\begin{enumerate}
    \item \textbf{Untrusted content reaches the model.} Contingut que prové d'una font que el model ha de tractar com a dada (no com a instrucció): cossos de notes, correus, documents importats, o sortida d'una crida web.
    \item \textbf{Private data accessible.} El model té accés (directe via context o indirecte via tool) a informació sensible que un atacant voldria veure exposada.
    \item \textbf{External communication channel.} Existeix un canal pel qual el model pot retornar text fora del límit de confiança original (xat, email, webhook, eina de cerca, fitxer escrit).
\end{enumerate}

Cap dels tres factors aïllats és perillós. Un LLM que llegeix contingut hostil però sense accés a dades privades simplement retorna una resposta neutralitzada. Un LLM amb accés a dades privades però sense canal extern d'exfiltració pot, com a molt, mostrar-les al mateix usuari autenticat (que ja les podria veure d'altres maneres). Un LLM amb canal extern però que mai veu contingut hostil tampoc és vulnerable, perquè cap actor li està dirigint les instruccions.

L'arquitectura de Synapse Notes és exposada precisament a aquesta intersecció: el servidor MCP exposa eines que llegeixen el contingut de l'usuari (que un atacant podria embolicar amb instruccions ocultes), que tenen accés a la base de dades privada del propietari (via JWT) i que retornen text a agents externs (Claude Desktop, agents personalitzats, futurs ChatGPT plugins). El disseny de seguretat ha de fer que les tres potes coexisteixin sense convergir en cap path d'execució real.

Willison documenta diversos incidents públics el 2023-2025 com a instàncies estructuralment idèntiques d'aquest patró \parencite{willison2025trifecta}, entre ells filtracions a Microsoft Copilot via documents Office, exposicions a Slack AI via missatges directes i un XSS via comentaris d'issues a GitLab Duo. Cada cas és diferent en superfície (correu, missatges, comentaris) però estructuralment idèntic: contingut hostil entra al context, dada privada accessible, i un canal de sortida que el converteix en exfil real.

La figura~\ref{fig:lethal-trifecta} visualitza la convergència de les tres potes al servidor MCP de Synapse Notes: la única eina del catàleg que satisfà totes tres és \texttt{summarise\_notes}, justificant la concentració del filtre D3 sobre aquesta eina sola.

\subsection{Anàlisi de risc residual per eina}
\label{sec:risk-residual}

\paragraph{summarise\_notes (alt risc, mitigat).} Trifecta completa. D3+D2+D4 actuen en sèrie. L'avaluació empírica (\S\ref{sec:red-team-promptfoo}) mostra 0/30 exfiltracions reals tant amb D3 actiu com desactivat, perquè D2 sol ja captura tot el suite. El risc residual és el long tail no provat: 30 atacs en 5 categories no esgota l'espai de paràfrasis automatitzades. Mitigació futura proposada: ampliar la suite a 200--500 variants i mesurar la corba precision-recall del threshold del judge.

\paragraph{search\_notes, get\_note, graph\_neighbors, graph\_shortest\_path (risc mig, mitigat).} Aquestes eines llegeixen contingut potencialment hostil i el retornen al client MCP. El risc és que l'agent client (Claude Desktop) processi el contingut amb les seves pròpies eines i caigui en una trifecta indirecta. Mitigació pel servidor: retornar estructura (ids, similaritats, edge kinds) en lloc de text lliure sempre que la semàntica de l'eina ho permet. La responsabilitat última de mitigar prompt injection al costat client recau sobre el host MCP (D2: \emph{host confirmation} de cada tool call abans de fer-la executar).

\paragraph{create\_note, update\_note, tag\_notes (risc baix, mitigat).} Aquestes eines escriuen però no llegeixen abans d'escriure. No hi ha contingut downstream que un LLM resumeixi com a part de la mateixa traça. La mitigació primària és D2 \emph{host confirmation}: el host MCP (Claude Desktop) ha de demanar permís a l'usuari abans d'invocar cap d'aquestes eines, perquè podrien ser encadenades després d'una resposta de \texttt{summarise\_notes} comprometuda. La seqüència d'atac defensable és: (1) atacant amaga instrucció a una nota; (2) usuari demana resum; (3) sumaritzador retorna text amb instruccions ocultes per al host; (4) host crida \texttt{create\_note} per exfiltrar a una nota nova. D2 trenca el pas (4).

\paragraph{Agents implementats.} Els dos agents en segon pla descrits a \S\ref{sec:disseny-agents} (\texttt{auto-tag} i \texttt{weekly-digest}) operen sota la mateixa anàlisi Lethal Trifecta. \texttt{auto-tag} crida Haiku~4.5 però no exposa el resultat directament: les propostes s'escriuen a \texttt{tag\_suggestions} amb estat \texttt{pending} per a aprovació humana (mateix patró D2 \emph{host confirmation} traslladat a la UI). \texttt{weekly-digest} no involucra cap LLM (només queries SQL). La capa més rellevant per a tots dos és D4 (cost guards): l'execució via Vercel Cron protegida per \texttt{CRON\_SECRET} + verificació de la D4 allowlist evita que un endpoint exposat consumeixi quota sense control. Cada agent escriu a \texttt{agent\_events} amb el seu action + payload, deixant signatura auditable de qualsevol invocació.

\subsection{Limitacions del disseny}
\label{sec:security-limitations}

Aquest disseny no resol tres classes d'atac que queden documentades com a treball futur o limitacions acceptades:

\begin{itemize}
    \item \textbf{End-to-end encryption}. Les notes són emmagatzemades al servidor de Supabase en clar (amb encryption at rest del proveïdor però no E2EE). Un compromís del compte Supabase exposaria tot el contingut. Mitigació prevista al \S\ref{ch:annex-install} d'instal·lació: la base de dades pot ser un Supabase self-hosted del propi usuari.
    \item \textbf{Side-channel timing}. La diferència de latència entre el path "judge bloqueja" i "judge permet" (\S\ref{sec:red-team-promptfoo} mostra mean 2363 ms vs $\sim$3500 ms quan el sumaritzador també corre) és teòricament observable per un atacant que pugui mesurar el temps de resposta. No es considera explotable a l'escala actual (1 usuari allowlistat) però seria mitigable amb un timing jitter aleatori al wrapper de \texttt{summarise\_notes}.
    \item \textbf{Compromise de la cadena de proveïdors}. Una actualització maliciosa d'\texttt{@ai-sdk/anthropic} o de \texttt{@modelcontextprotocol/sdk} podria comprometre el sistema. Mitigació actual: tots els paquets són d'autors oficials i versionats al \texttt{package-lock.json}. Una capa addicional de defensa seria un mirror privat amb auditoria, fora de l'abast d'un TFG.
\end{itemize}

\textbf{Honestedat metodològica}: aquest disseny no és un panaceu i no s'auto-presenta com a tal. La secció~\ref{sec:red-team-promptfoo} de l'avaluació documenta explícitament que en el suite de 30 atacs, el guany marginal de D3 sobre D2 sol és 0\%. La defensa de D3 reposa en quatre arguments operatius (signatura estructurada auditable, earlier rejection, resilència a regressions del model upstream, mostra petita amb long tail no explorat) i no en una afirmació de millora absoluta de la seguretat. Aquesta postura és intencional: vol evitar les promeses de "AI security" que no s'aguanten quan són examinades quantitativament.

\section{Disseny de la interfície}
\label{sec:disseny-interficie}

El disseny d'interfície de Synapse Notes prioritza la \emph{visibilitat de l'estat} i la \emph{reversibilitat de les accions destructives}. Aquesta secció documenta els principis aplicats, la jerarquia visual, i les superfícies UI principals; la implementació concreta de cada component està al capítol~\ref{ch:implementacio}.

\subsection{Principis de disseny}

\paragraph{Optimisme amb fallback honest.} Les mutacions sobre notes (star, archive, delete, restore, duplicate) es renderitzen \emph{immediatament} a la UI via \texttt{useOptimistic} de React 19 abans que el servidor confirmi el resultat. Si la Server Action falla, l'estat optimista es reverteix automàticament. Aquest patró està descrit al detall a la secció~\ref{sec:optimistic-ui}, però la decisió de disseny és prèvia: \emph{el lag de xarxa no ha de ser perceptible per l'usuari per a operacions que tenen una probabilitat de fallada $<$1\%}.

\paragraph{Reversibilitat de l'arxivat.} La columna \texttt{notes.archived\_at} és una \emph{soft delete}: l'usuari pot recuperar una nota arxivada en un sol clic des de la vista d'arxiu. Cap operació de la UI principal causa pèrdua irrecuperable de dades. L'única operació de \emph{hard delete} és l'eliminació definitiva, sempre amb confirmació via \texttt{AlertDialog} (component shadcn).

\paragraph{Llibreria visual coherent.} Tot l'inventari de primitives UI ve de shadcn/ui sobre Radix Primitives, amb tema personalitzat (paleta amber + slate + violeta per als backlinks). La decisió de no incorporar Material UI ni Chakra elimina una capa de dependència de bundle considerable; shadcn copia les implementacions al projecte (no és un \emph{npm package}) i això permet personalitzar-les sense conflictes d'upgrade.

\paragraph{Accessibilitat com a defecte, no com a opcional.} Cada component Radix porta ARIA attributes correctes per defecte; el tema custom respecta el contrast WCAG 2.1 AA tant en mode light com dark. Les drecera de teclat (vegeu \texttt{KeyboardShortcutsDialog}) inclouen la deteció de plataforma per a pintar correctament \texttt{Ctrl} (Win/Linux) vs \texttt{Cmd} (macOS).

\paragraph{Internacionalització nativa.} Tres idiomes simultanis (català, espanyol, anglès) amb un \texttt{LanguageProvider} basat en \texttt{localStorage}. La selecció no recarrega la pàgina, només re-renderitza les strings traduïdes. El català és l'idioma per defecte i el que s'utilitza al memoir.

\subsection{Today's Brain (decisió de disseny específica)}
\label{sec:disseny-todays-brain}

La \emph{Today's Brain card}, al cim del dashboard, és un experiment de disseny que demostra l'aprofitament del corpus per a generar valor proactiu. Cada vegada que l'usuari obre la pàgina principal, una crida server-side a Haiku 4.5 (gated per Suspense per a no bloquejar el render) genera tres bullets resumint què ha escrit en els últims 7 dies, més top 3 tags actius i un sparkline d'activitat dels últims 14 dies. La card és l'única superfície on l'usuari no ha d'invocar manualment l'IA: ve donada.

Aquesta decisió contradiu lleugerament el principi de \emph{IA com a eina, no com a sistema}: en aquest cas l'IA s'executa sense petició explícita. Es justifica perquè (a) el cost és reduït (una sola crida Haiku per pageload, ~\$0.003), (b) la informació generada és resum de dades que l'usuari ja té (no en cap inferència nova), i (c) el resultat és \emph{informatiu i no executable}: la card mostra text, mai dispara accions. És el patró \emph{ambient AI} aplicat amb restricció.

\subsection{Drawer d'agents (disseny pendent d'implementació)}

El plan original (vegeu \S\ref{sec:disseny-agents}) preveu un \emph{ActivityDrawer} accessible des del header, que mostra els últims events de \texttt{agent\_events} amb timeline. Per a propostes d'auto-tag, una variant del drawer mostra cards d'acceptació/rebuig amb la nota afectada i el tag proposat. La UI del drawer queda documentada a \S\ref{ch:valoracio} com a punt de polit post-entrega; els agents ja escriuen els events i el corpus d'inputs està disponible per a consulta directa a la BD.
